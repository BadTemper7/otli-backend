# OTLI backend: API-wide 30-second timeout diagnostics and safer failure handling

## Purpose and scope

This package builds on the **registration-only-email and registration-upload-timeout** version of the newly uploaded OTLI backend. The 30,000 ms Axios timeout reported on multiple client/admin APIs suggests a shared infrastructure, database, proxy or frontend timeout—not necessarily SMTP.

The update makes database outages fail clearly and adds visibility for slow requests. **It does not guarantee that slow queries or hosting bottlenecks will be resolved**, and has not been executed against live Hostinger or MongoDB Atlas.

**No new `.env` variables, npm packages, Redis, database indexes, API route changes, or migrations.** SMTP remains allowed **only** for registration OTP and resend. Booking status notifications remain **in-app**. Existing CORS and Hostinger startup configuration are intentionally retained.

## Changes

1. `server.js` uses a bounded MongoDB connection selection window (12 seconds), connection establishment timeout (10 seconds) and pool checkout wait (8 seconds), with a limited pool size of 20 and idle reaping. These settings avoid some **30-second waits** when MongoDB is unreachable or the pool is exhausted; they do not accelerate slow queries.
2. `middleware/databaseAvailability.js` returns HTTP **503** with `DATABASE_UNAVAILABLE` and `Retry-After: 5` immediately if MongoDB is disconnected. It covers `/api/*` except the database-independent `/api/test` check.
3. `middleware/apiErrorResponse.js` translates driver connectivity/time-limit failures into safe HTTP **503** errors and distinguishes upload-size errors (**413**). Internal error messages and connection strings are not sent to browsers.
4. `middleware/apiDiagnostics.js` adds an `X-Request-ID` header and records slow (>= 3s), server-failed and disconnected requests with the **registered route pattern**, elapsed time, HTTP status and database state. It does not log email addresses, URL query strings, tokens, OTPs or documents.
5. `GET /health/database` uses a read-only MongoDB ping with an approximately 3-second response deadline and returns `mongodb: reachable | unresponsive | disconnected` and `latencyMs`. No private connection details are exposed.
6. Database connection loss/restoration produces brief sanitised log entries.

## Diagnose production without sending email

Check these URLs on the **API host** (not the React client/admin host):

```
GET /api/test
GET /health
GET /health/database
```

- `/api/test` fails or returns Hostinger HTML 503: Node.js app, reverse proxy, deployment, or hosting resources are likely affected. A database guard cannot solve a process which never starts.
- `/api/test` works but `/health/database` is 503/slow: MongoDB Atlas network, IP allowlist, credentials, DNS, pool exhaustion, or connectivity is a likely cause.
- Both tests return 200 rapidly but a specific `/api/...` endpoint times out: inspect its query/index, payload size, computation, disk operations, or external service. Inspect `[api]` and registration-specific timing logs.
- Requests return 429: that's the intentional, shared registration SMTP rate limit—not an API timeout.

**Illustrative log only** (not an actual measurement):

```
[api] slow request id=... method=GET route=/api/admin/bookings status=200 totalMs=6200 db=connected
[api] server error id=... method=GET route=/api/client/bookings status=503 totalMs=12015 db=disconnected
[api] client/proxy disconnected id=... method=POST route=/api/auth/client/register/request-otp status=200 totalMs=30001 db=connected
[database] MongoDB connection lost
```

Look for `/api/admin/reports` and large storage-visualization endpoints if only those become slow with increasing numbers of records. They may need selective query optimization after logs identify the specific route; do not change their API responses speculatively.

## React / Axios side

An Axios exception such as **`timeout of 30000ms exceeded`** is generated by its client request timer. The backend cannot override it. Find the shared Axios configuration in **both** React applications (not included in the backend ZIP) and inspect any `timeout: 30000` setting.

Do **not** blindly increase all API timeouts to hide slowness. For legitimately slow read-only exports, consider a specific longer timeout after measuring them. For registration with file uploads, keep the prior request-specific 120-second timeout if Hostinger's proxy permits it. **Do not automatically retry** registration OTP, booking creation, payment or other state-changing requests after a timeout: the server may have already committed the operation.

If the browser says CORS rather than timeout, check the actual failed response and request origin; these are separate issues. This patch does not change CORS allowlists.

## Safe installation

1. Back up the running Hostinger backend and existing `.env` privately.
2. Deploy the complete ZIP, or merge only the files from the changed-files ZIP.
3. Keep the same `npm start` (`node server.js`), MongoDB/SMTP environment variables and dependencies.
4. Run `node --test tests/*.test.js` in a safe development/staging environment.
5. Restart the app, check `/api/test`, `/health` and `/health/database`.
6. Trigger only **authorized test actions** in client and admin, then review `[api]` runtime log entries and response request IDs.

If the app still returns Hostinger HTML **503 immediately**, inspect runtime logs and startup prerequisites. Startup still waits for successful MongoDB connection and document storage. A bad database URI or blocked Atlas network can prevent startup completely.

## Test status

29 offline tests passed using Node's built-in test runner. Tests cover existing registration OTP and email cap safety, upload/SMTP error handling, API database fail-fast, sanitized errors, request timings, and a mocked database health ping. Syntax checks pass across all project `.js` files. **Live MongoDB, SMTP, Hostinger process/proxy and React browser integration were not tested**, and the npm dependencies were not installed in this environment.

## Unresolved operational risks

- MongoDB Atlas access-list/network/DNS latency and resource limits need production logs to confirm.
- Slow indexed/unindexed queries, report aggregation and large JSON payloads can still take more than a browser's 30-second deadline.
- Hostinger reverse proxy timeouts and application resource caps cannot be fixed by an Express middleware alone.
- Existing original CORS setup is intentionally unchanged here; fix independently if credentialed requests still fail CORS checks.
- Check frontend Axios behavior, especially global timeouts and accidental retry interceptors.
